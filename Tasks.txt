Цель

Сделать многоклавиатурный USB HID (xHCI) ввод так, чтобы:

любые N клавиатур работали параллельно,

события обрабатывались строго по источнику (endpoint → handle),

ввод и автоповтор были корректны и не блокировали другие устройства,

отсутствие “глобального фокуса” на одной клавиатуре,

TRB для interrupt-IN всегда перезаряжается, устройство никогда не “застревает”.

0) Термины и сущности (зафиксировать)

kbd_handle (h) — индекс устройства/инстанса клавиатуры.

epu — endpoint pointer / identifier из xHCI event (то, по чему мы мапим событие на endpoint).

kbd_meta[h] — состояние клавиатуры (endpoint, ring, буферы, флаги, тайминги).

IN interrupt endpoint — единственный источник репортов клавиатуры.

re-arm — постановка следующего Normal TRB на interrupt-IN ring + doorbell.

ep_id / ep_addr (или то, чем ты оперируешь при doorbell)

epu (ключ для map epu→handle)

Очередь и буферы:

указатель на ring (TRB ring для interrupt-IN)

ring_idx, cycle (или любые твои индексы)

report_buf (куда DMA пишет репорт)

report_len

Синхронизация/состояние репортов:

has_report (bool) — в буфере есть свежий репорт

in_flight (bool) — TRB поставлен, ждём completion

seq/gen (счётчик репортов, удобно для отладки)

Логика клавиатуры:

last_keycode / pressed_bitmap (опционально, но “взросло” — лучше bitmap)

repeat структура (см. ниже)

2) Контракт обработки событий xHCI (строго)
Требование

Обработчик event ring НЕ должен “печатать символы” и заниматься консолью напрямую (это как ISR/bottom-half).

Он должен делать ровно:

распознать тип события (Transfer Event),

достать epu,

найти h по epu,

обновить kbd_meta[h]:

has_report = true

in_flight = false

сохранить статус/len (если ты читаешь length из event TRB/status)

немедленно запланировать обработку (work item / очередь событий).

В драйверах это обычно:

ISR → кладёт “completion record” в lock-free очередь

worker thread → делает разбор HID и отдаёт в input subsystem

3) Очередь событий (мульти-девайс)
Требование

Сделать общую очередь “kbd_event_queue”, куда кладутся записи вида:

kbd_event { handle h, type=REPORT_READY, gen=seq, timestamp }

Пуш делает event-обработчик.

Поп делает worker/основной цикл консоли.

Важно: очередь должна позволять несколько событий подряд от разных handle без потерь.

4) Worker: обработка HID отчёта
Требование

Worker должен работать так:

Для каждого REPORT_READY(h):

взять meta = kbd_meta[h]

прочитать report_buf (8 байт boot keyboard или по report descriptor если non-boot)

преобразовать в “нажатия/отпускания”:

минимум: определить keydown/keyup по сравнению с прошлым состоянием

отправить символ(ы) в консоль через единый интерфейс (console_submit_key(h, key_event))

Консольный интерфейс

console_submit_key(handle, key_event) должен:

быть независим от USB

принимать “событие клавиши” (keycode + press/release + modifiers)

5) Автоповтор “по-взрослому”
Требование

Повтор — не глобальный, а на уровне консоли или на уровне handle, но с правильной семантикой.

Стандартная схема:

повтор зависит от “последней активной клавиши”, но источник всё равно конкретный handle

реализация хранит:

repeat_handle

repeat_key

repeat_next_deadline_ticks

repeat_active

Где хранить:

лучше в консоли (input layer), потому что repeat — часть UX, а не USB.

но repeat_handle обязателен, чтобы не было залипания на handle=0.

6) Re-arm TRB: железобетонное правило
Требование (ключевое)

Для каждого handle после completion (Transfer Event) нужно гарантированно:

подготовить следующий Normal TRB на interrupt-IN endpoint ring:

DMA addr = meta.report_buf

len = meta.report_len

IOC=1 (чтобы снова получить event)

обновить ring_idx/cycle

позвонить в doorbell нужному endpoint

Это должно происходить:

либо в event-обработчике (как “fast path”)

либо в worker, но тогда in_flight должен быть защищён от гонок

Взрослая гарантия: “в любой момент для каждого interrupt-IN endpoint либо стоит активный TRB (in_flight), либо он будет поставлен немедленно после обработки completion”.

7) Map epu → handle (детерминированно)
Требование

Сделать структуру отображения:

epu_map[epu] = handle (если epu небольшое/упакованное)
или

хеш/линейный поиск по kbd_meta[].epu, но тогда N маленькое и это осознанно

И добавить проверки:

если epu неизвестен → лог + игнор события (не падать)

8) Состояния и инварианты (для отладки и стабильности)

Определить и поддерживать инварианты:

Для каждого handle h:

in_flight == true ⇒ has_report == false (обычно)

после Transfer Event: in_flight=false, has_report=true

после обработки report: has_report=false

после re-arm: in_flight=true

Любое нарушение — печать диагностической метки.

9) Трассировка “взрослая”, но точечная

Добавить структурированный лог (fb-метки достаточно) в 3 местах:

Transfer Event:
TE epu=X h=Y len=L status=S inflight->0 has_report->1 seq++

Worker parse:
RP h=Y seq=... kc=.. mods=.. keys=..

Re-arm:
ARM h=Y ring_idx=.. cyc=.. db=.. inflight->1

Это даст 100% доказательство, что:

события приходят,

на правильный handle,

репорт реально обработан,

TRB перезаряжен.

10) План внедрения (по коммитам)

Ввести kbd_meta[] (полные поля) + map epu→handle.

Убрать глобальные usb_pending/usb_repeat/usb_kbd_*.

Сделать очередь kbd_event_queue.

Переделать event-обработчик: только completion → очередь.

Сделать worker: parse report → console_submit_key.

Реализовать repeat в консоли с repeat_handle.

Встроить “железную” re-arm логику и инварианты.

Стресс: 2–3 клавиатуры, быстрый набор, одновременные нажатия.


Сейчас глобальные состояния (usb_pending, usb_kbd_ring, repeat и т.д.) всё ещё мешают параллельному вводу — обработка событий, очистка
  буферов и re-arm привязаны к “первой” клавиатуре. Чтобы полностью перейти на описанную архитектуру, нужен крупный рефакторинг:

  1. kbd_meta[h] нужно расширить (ring pointer, report buffer, ring indices, has_report, in_flight, seq, slot/ep, doorbell, состояние
     repeat). Все текущие глобальные переменные должны быть удалены; вместо них нужно ссылаться на поля выбранного handle.
  2. Event handler должен только сопоставлять ev_epu → handle, обновлять in_flight/has_report/seq и ставить kb_event_queue (например,
     circular buffer ptr), где REPORT_READY хранит handle + seq. Никаких line_apply_char тут.
  3. Worker loop (в основном цикле) должен вычитывать из kbd_event_queue события, читать report из kbd_meta[h].report_buf, сравнивать с
     прошлым состоянием (bitmap/previous report), генерировать key_event и вызывать console_submit_key(h, key_event). После обработки
     has_report = false.
  4. Re-arm — сразу после получения completion (в обработчике) нужно подготовить Normal TRB (DMA = report_buf, len = report_len, IOC=1),
     обновить ring_idx/cycle, звонить doorbell и выставить in_flight = true; если TRB не заряжен — печатать ARM лог.
  5. console_submit_key должен хранить repeat-данные (handle, key, deadlines). Повтор не должен быть глобальным по клавиатуре: как только
     придёт новый keydown с другим handle, repeat_handle переключается, предыдущая клавиатура теряет repeat.
  6. Трассировка: добавить метки TE epu=.. h=.., RP h=.. seq=.. kc=.., ARM h=.. ring_idx=.. чтобы видеть весь путь.

  Это объёмный рефакторинг, требующий переписывания событий/очереди, метаданных и repeat-логики. Если нужно, могу шаг за шагом реализовать
  (kbd_meta расширение → очередь → worker → repeat → re-arm), но потребуется значительное время. Какой кусок сделать первым?
